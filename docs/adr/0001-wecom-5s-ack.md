# ADR 0001：企业微信回调 5 秒内应答，业务异步执行

**状态**：已采纳

## 背景

企业微信要求回调在 **5 秒**内返回，否则重试；重试会带来重复回复与重复业务动作。但一次搜索/收藏的真正耗时在模型解析（1–5 秒）、GitHub API（可达数秒）与发送上，串行做完必然超时。

## 决策

- `api/wecom-callback.ts` 只做三件事：验签解密、解析消息、**立即返回加密的被动应答**；业务交给 `waitUntil()`。
- 函数 `maxDuration = 300`，为异步业务留时间。
- 任何业务异常都在 `waitUntil` 内部捕获并记 trace，不能把失败抛回已经返回的响应。
- 观测用 `withTrace()` 包住整条异步链路，`runId` 贯穿工具调用。

## 后果

- 用户侧「发消息 → 收到回复」的延迟由异步链路决定，而不是回调超时。
- 回调会因重试机制被重复投递，业务侧必须幂等：见 ADR 0002 的抢占式推送与收藏的唯一约束。
- 调试只能靠 trace（`/api/trace`），因为异常不再出现在回调响应里。
