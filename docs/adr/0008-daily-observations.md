# ADR 0008：今日观察——讲变化、防重复、没有新主题就不发

**状态**：已采纳（2026-10-29）

## 背景

用户希望简报不只是榜单，而是「社区今天在集中解决什么问题」的判断。直接把当天榜单丢给模型写一段概览的问题有两个：

1. **每天都很像**：榜单变化不大时，模型会换词复述同一批仓库，用户读两天就腻；
2. **没有证据**：一段泛泛的「AI 工具持续火热」既不可验证，也不比榜单多信息。

另一个实现陷阱：`digest-snapshot:<date>` 在 kv_cache 里只有 **24 小时 TTL**，第二天就过期，不能拿来算 7 天趋势。真正的历史在 `trending_entries`（每天每榜每仓库一行，无清理任务）。

## 决策

- **事实由代码算，不由模型编**。一条 SQL 从 `trending_entries` + `repos` 计算每个仓库的 7 天表现：首次出现、连续在榜天数、今天/前一数据日增量、排名变化；另一条 SQL 算语言/话题的每日数量。
- **候选类型固定**：新上榜（首次出现 = 数据日）、加速（增量 ≥200 且 ≥昨日 1.8 倍，或排名跃升 ≥5）、连续在榜（≥3 天且仍有增量）、主题变化（语言 ≥3 / 话题 ≥4，且 ≥1.5 倍基线、绝对增加 ≥2）。泛平台话题（android/ios/macos/windows 等）直接排除。
- **模型只写句子**：输入是候选事实与证据仓库的功能短句，输出 2–3 条 ≤80 字的中文观察，每条对应一个候选编号；证据仓库与签名由代码从候选带入。`claim` 里的数字必须出现在候选事实里，否则整条丢弃；仓库名不强制点名——渲染层在判断没点名时只补一个锚点仓库（不堆列表）。生成结果里带 `debug`（原始 claim 与丢弃原因计数），用于调提示词与阈值，不发给用户。
- **7 天去重**：每天的结果写 `observation:v1:<date>`（8 天 TTL）。新观察命中以下任一条就丢：相同签名在 7 天内出现过；证据仓库有 ≥2 个在 7 天内的观察里出现过。允许一个仓库以新语境回归。历史读取失败 **fail closed**（当天不生成），因为重复正是这个功能要避免的缺陷。
- **少于 2 条就不生成**。全部被去重/校验掉时缓存一份空结果，避免每小时重复调用模型；数据日变化时才重建。
- **全局共享一份，不按用户个性化；只生成并写入 `archive:v1:<date>`，不在微信推送**。微信每天只发一条简报（用户反馈两条推送是信息骚扰）；观察在面板「历史」里回看。
- **观察绝不影响简报**：生成/归档的任何失败都只记 trace，简报照常。**模型失败时当天不生成观察**——不回退到「候选事实堆叠」，因为只有数字、没有总结的推送就是信息噪音（用户明确反馈过）；模型正常但输出被白名单丢弃时同样不生成。
- **归档 30 天**：同一次生成写 `archive:v1:<date>`（观察文本 + 当天 top 8 条目），供后续 H5 面板的历史页使用。

## 后果

- 有些天不会有观察（没有真正的新主题）。这是有意的：用户收到的仍是简报，而不是一段重复的套话。
- 阈值（1.8 倍、3 天、1.5 倍、2 条证据）是产品参数，需要观察两周后按 trace 调整。
- 每天多一次共享 LLM 调用（15s 超时），不随用户数增长；不新增 Serverless Function，也不需要迁移。
- 观察是全站共享的，订阅了特定语言的用户可能看到不相关主题；个性化留到以后，用成本换一致性。

## 备选方案（未采纳）

- 用 `digest-snapshot` 历史做对比：TTL 24h，不可用。
- 每个用户单独生成观察：成本与延迟随用户数线性增长，收益不明。
- 每天都发一段概览：会退化成换词复述，正是要解决的问题。
