# ADR 0005：规则前置，模型只在拿不准时参与

**状态**：已采纳

## 背景

每条入站消息都先过一次模型可以换来更自然的理解，但代价是：每条消息都有延迟与 token 成本、模型故障会拖垮基础功能、而且大部分消息其实是固定指令（「帮助」「我的收藏」「订阅 python」）。这个项目还要面对「用户没配自己的 key」的真实情况。

## 决策

- 第一层是**纯函数路由** `decideTextRoute()`（`src/wecom/route-decision.ts`）：命令、用法提示、疑似缺参数都在这里判定，不碰网络、不碰数据库，评测可以逐条回放。
- 第二层是**规则意图** `classifyByRules()`：只要明显是「关于本应用」或「完全无关」，直接回文案，不检索、不写 `search_caches`。
- 第三层才是模型：用户配了自己的 key 才走结构化解析与工具循环；没配就是 `{ kind: 'none' }`，规则解析 + 只读共享缓存，**零模型调用**。
- 工具链路同样规则前置：只有「点名仓库 / 深挖 / 靠不靠谱 / 改订阅」这类消息才进工具循环，普通搜索留在零模型路径。
- 解析结果按提示词版本缓存（`parse:v1`），改提示词必须 bump 版本，否则线上继续用旧结果而评测看不见。

## 后果

- 常见指令的延迟是毫秒级，且模型挂掉不影响它们。
- 规则漏判要能兜住：拿不准一律按搜索处理——漏判退化成老行为，不会误伤正常提问。
- 规则本身成了需要维护与评测的资产（见 ADR 0006）；漏判样本通过匿名意图日志收集，用来反推下一批规则。
