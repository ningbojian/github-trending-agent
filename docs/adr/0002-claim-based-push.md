# ADR 0002：抢占式推送——条件 UPDATE，失败回滚

**状态**：已采纳

## 背景

`digest-hourly.yml` 每小时调用一次推送端点，多个 tick 可能重叠（函数执行超过一小时、手动重试、并发实例）。若「先读 `last_digest_at` 再写」，两个 tick 会同时判定「该发」并各发一份；用户收到重复简报。

## 决策

- 发送前用**条件 UPDATE 抢占**：只有当 `last_digest_at` 仍满足时间窗时才写入当前时间，`UPDATE ... RETURNING` 为空即表示抢占失败，本轮跳过。
- 抢占成功后才构建并发送；发送/构建失败则**回滚** `last_digest_at`，让下一个整点重试。
- 抢占语句自身抛错视为「未生效」，不回滚（否则会把别的基础设施问题写进业务状态）。
- 整轮 fan-out 有 240 秒预算；超预算的订阅者不抢占、留到下一个整点。

## 后果

- 重复推送从「可能」变成「结构上不可能」，代价是每次都要多一条 UPDATE。
- 「已抢占但函数被杀」的窗口仍然存在，靠回滚 + 下一 tick 兜底；回滚失败会晚一天，但不会重复。
- 用户手动退订/改时间不影响已抢占的那一次，属于可接受的时间窗语义。
