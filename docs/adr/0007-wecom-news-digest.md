# ADR 0007：企微每日简报用 news 卡片，8 篇封顶

**状态**：已采纳（2026-10-28）

## 背景

简报一直是单条纯文本：每天 10 行「仓库 + 星标 + 中文简介 + 裸链接」。用户反馈「密密麻麻，不想看」，希望换成带图片的卡片。企微可选的富文本类型只有 `textcard` 与 `news`，而它们的实际行为在个人微信里没有权威文档，只能实测。

2026-10-28 用一个临时端点（已删除，见 `docs/deploy.md` 第 3 节）在个人微信逐条实发，得到以下硬约束：

- `news` 一条最多 **8 篇**；第 9 篇被 `45008 article size out of limit` 拒绝。
- 多篇布局里**只有标题可见**，`description` 完全不显示（无论第几篇）。
- 标题在客户端约 **10–12 个汉字**处被裁，128 字节的 API 上限远不是显示上限。
- 第 1 篇是大图 + 标题；第 2 篇起是方形缩略图 + 标题。
- 缩略图由**企微自己的服务器**去抓 `picurl`：直连 `avatars.githubusercontent.com` 或经 Vercel rewrite 反代都会随机失败（8 张里常有 3 张只剩灰头像）。
- `textcard` 能显示，但一次只能放一个仓库，且 `btntxt` 按钮文字不显示。
- `markdown` 仍然只在微信里显示「暂时不支持此消息类型」。
- news 卡片**没有操作按钮位**，任何「换一批 / 收藏」都只能靠用户回文字命令。

## 决策

- 每日简报改为**一条 news，最多 8 篇**。默认条数与上限都从 10/20 收到 8；「条数 N」命令同步改为 1–8。邮件通道不受影响（自己有 5/10/15/20）。
- **第 1 篇**用 GitHub OG 海报（`opengraph.githubassets.com`，实测稳定）：大图里自带仓库名与英文简介。
- **第 1 篇**用仓库 OG 海报（宽图）；**第 2–8 篇**用 owner 头像的方形缩略图，**自托管**在 `docs/avatars/<owner>.png`（静态文件，不经第三方），manifest 里没有的 owner 回退到品牌图标 `docs/assets/icon-750.png`。两端发**同一份 picurl**，避免「手机无图、电脑留占位」的冲突；仓库 OG 小图会被裁成文字截图，owner 头像更稳也更像图标。
- 标题结构固定为 `🔥/🆕 序号. owner/repo ★星标 (+增量)｜≤18 字短简介`：
  - 仓库名最先出现——尾部一定会被裁；
  - `🔥` 给**增长率**（`+增量 / 总星标 ≥ 5%`，且增量 ≥ 100）里最高的 1–2 条。按绝对增量取前二会永远锁死在榜单第 1、2 名，和基量无关；
  - 否则 `isNew` 用 `🆕`（二选一，省空间）；
  - 不做语言标签：对扫读帮助不大，还会挤掉简介空间；
  - 短简介由模型**单独生成**（≤18 个汉字、完整短语），不是把 28 字简介硬切；拿不到就退回完整分句，再不行宁可不写——绝不出现半句加省略号；
  - 整条标题严格 ≤128 字节，极长仓库名也先保证不触发企微拒收。
- **Overview Abstract 不进微信**：8 个位置每个点开都该是真实仓库；概览卡点开没有去处，还要牺牲 12.5% 的信息量。概览继续留在邮件版。
- news 发送失败（errcode/网络）**回退到原来的纯文本简报**，绝不重复发送；`entries` 始终与消息实际顺序一致，`收藏 N` 继续可用。
- 排序保持现状：近 7 天新增星标降序（不是总星标）。

## 后果

- 用户扫一眼就能看到 8 个仓库，第一条有大图；每条有一句「能做什么」的完整短句（≤18 字），详情要点开 GitHub——这是客户端截断决定的，不是取舍。
- 图片只保留首篇一张，其余靠文字；换来的是一眼可见的稳定版式，代价是列表不如全卡片「花哨」。
- Hobby 套餐每个部署最多 12 个 Serverless Function。`tests/vercel-config.test.ts` 会拦住第 13 个；本项目最终 11 个（临时探针已删除）。
- 没有操作按钮：`收藏 3` 等命令继续作为唯一交互入口；「换一批」若要实现，只能做成文字命令，不能指望卡片按钮。
